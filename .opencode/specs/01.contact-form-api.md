# Spec: Contact Form API

## Overview

Add a functional contact form beneath the existing contact info cards on the portfolio. The form sends visitor messages to a Next.js Route Handler (`/api/contact`) which processes and stores the submission. A success/failure toast alerts the user without a page reload. This turns the static Contact section into an interactive touchpoint.

## Depends on

- Contact section in `src/components/Contact.tsx`
- Toast context in `src/components/Toast.tsx` (already wired into `page.tsx`)
- Design tokens in `src/app/globals.css` / `tailwind.config.ts`

## Routes

- `POST /api/contact` — Next.js Route Handler that accepts `{ name, email, message }` and returns a JSON response. No new pages.

## Components

- **Modify:** `src/components/Contact.tsx` — add a form below the existing contact info cards. Use `"use client"` directive. Wire form submit to fetch `/api/contact` and show a toast on success/failure.

## Data changes

No data file changes. The contact handler will write to a file or log (no database required).

## Files to change

- `src/components/Contact.tsx` — add the form UI and client-side submit logic

## Files to create

- `src/app/api/contact/route.ts` — POST handler

## New dependencies

No new dependencies.

## Rules for implementation

- Reuse existing `bp-*` classes and design tokens from `globals.css` — don't introduce a new visual style without flagging it first.
- Keep content data-driven: copy, links, and structured content belong in `src/data/*.ts`, not hardcoded inline in components.
- New sections should use the existing `SectionHeading` component so headers stay consistent.
- Use a Next.js Route Handler (`src/app/api/.../route.ts`) — do not introduce a separate Express server.
- Use the existing `Toast` context via `useToast()` for success/error feedback.
- Form fields should use `bp-card` styling for input backgrounds. Use the existing Tailwind color tokens (`bg`, `card`, `line`, `ink`, `muted`, `amber`, `cyan`).
- The API handler should validate that `name`, `email`, and `message` are present and non-empty; return 400 with `{ error }` if invalid.
- On success, the API should return `{ success: true }` (actual email sending is out of scope for now — the handler can `console.log` the submission).
- The form submit button should use `bp-btn-primary`.
- Disable the submit button while the request is in-flight and show "Sending..." text.

## Definition of done

1. Visit `/` and scroll to the Contact section — a multi-field form (name, email, message) appears below the three contact info cards.
2. Submitting with empty fields shows a validation error via the toast.
3. Submitting with valid data shows a success toast ("Message sent!").
4. The network tab shows a `POST /api/contact` request with the form payload and receives a JSON response.
5. `npm run build` passes without errors.
